# SGW Hurricane Risk & Crew Coordination: Prototype

A lightweight prototype for the AECOM AI Solution Engineer case. It demonstrates the Phase 1 + Phase 2 workflow described in the PRD: as a hurricane's forecast track comes into view, every SGW electric grid asset is scored by composite risk (probability of failure × consequence), and the highest-risk assets get a recommended crew assignment, all as recommendations a human reviews and approves.

## Quick start

```bash
cd prototype
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
streamlit run app.py
```

The app bootstraps itself on first run: it generates all the mocked data and trains the risk model automatically if they aren't already present (`data/generate_data.py` and `model/train_risk_model.py` run once, then their output is cached). To regenerate from scratch, delete `data/*.csv` and `model/risk_model.pkl` and rerun.

To regenerate data or retrain manually instead of relying on the app's auto-bootstrap:

```bash
python data/generate_data.py
python model/train_risk_model.py
```

## What it demonstrates

Open the app and you'll see three tabs:

1. **Storm Overview**: Hurricane Helene's track and category as it approaches and crosses SGW's fictional territory, plotted against the asset grid. The sidebar slider controls how much of the track is "known so far," mirroring the PRD's ~6-hourly advisory refresh: move it earlier and the model only sees the storm's early, weaker, more uncertain position; move it later and the picture sharpens.
2. **Risk Ranking**: every asset scored and ranked by composite risk, with a map, a sortable table, and a per-asset explainability panel showing the top factors behind that score (e.g. high wind exposure, overdue inspection, dense vegetation).
3. **Crew Assignment**: the top-N highest-risk assets (N = number of available crews) matched to crews via a constrained optimisation step that minimises total travel distance, each with an explicit Approve/Reject action. Nothing is dispatched automatically.

Try moving the advisory slider from early to late and watching the risk ranking sharpen and reshuffle as more of the storm's path becomes known; that's the core workflow this prototype is meant to show.

## Architecture

```
data/generate_data.py - assets.csv, crews.csv, helene_track.csv, training_data.csv
risk_scoring.py - wind-field model, feature engineering, GBT training + scoring (shared by both the training-data generator and the live app, so training and inference always use the same pipeline)
model/train_risk_model.py - trains + saves the model from training_data.csv
optimisation.py - crew-to-asset assignment (Hungarian algorithm via scipy)
app.py - the Streamlit dashboard
```
This mirrors the PRD's architecture: a read-only ingestion/feature layer feeding a risk-model service, feeding an optimisation service, feeding a dashboard for human review. In this prototype the "ingestion" is reading local CSVs rather than live GIS/weather/maintenance APIs, since those systems don't exist for a fictional client; see Data & Assumptions below.

## Data & assumptions

**Real:** Hurricane Helene's landfall time, location, and intensity (~10 miles WSW of Perry, FL, 03:10 UTC 27 September 2024, Category 4, 140 mph) are the actual, publicly documented NHC figures. The storm's subsequent path through Georgia into the Asheville, NC area (which suffered the storm's most severe inland damage) is also real and well documented. The waypoints between these documented points, and their exact timing/intensity, are interpolated for this prototype rather than pulled from a full HURDAT2 best-track file, since that file wasn't retrievable in a usable form during development. Good enough to drive a realistic demo scenario; not a substitute for the real best-track record in a production system.

**Fictional, generated by `generate_data.py`:** everything about SGW itself. Thirty grid assets (substations and transmission lines) placed along Helene's real corridor, each with invented customers-served, criticality, age, maintenance history, vegetation density, and flood-zone attributes; eight field crews with base locations; and 1,200 synthetic historical storm-asset examples used to train the model. The historical examples aren't random: failure likelihood is generated from a designed function of wind exposure, storm surge, asset age, inspection gap, prior outages, vegetation, and flood zone, plus noise, so the trained model learns a genuine (if synthetic) relationship rather than fitting to noise. The held-out validation AUC is around 0.75, reported when you run `train_risk_model.py`.

**Wind-field model:** a simplified modified-Rankine-vortex profile (linear ramp to the radius of maximum winds, power-law decay beyond it) estimates wind speed at each asset's location from the storm's track and intensity. It's a standard simplification for this kind of exercise, not a production-grade parametric wind model (e.g. Holland 1980), and would be the first thing to swap out for something more rigorous if this moved beyond a prototype.

## Limitations

- Consequence is a static multiplier (customers served × criticality flag), not a network-topology/cascading-failure model, matching the PRD's deliberate MVP scoping decision.
- The crew-assignment optimiser is a simple one-to-one Hungarian-algorithm match on travel distance; it doesn't account for crew skills, shift limits, or multi-asset routing.
- Everything here runs locally against static CSVs. A real deployment would read from SGW's actual GIS, weather feed, maintenance, and workforce systems (all read-only, per the PRD's integration posture), and refresh automatically on the storm advisory cadence rather than via a manual slider.
- The model's ~0.75 AUC reflects a synthetic, deliberately noisy dataset built for demonstration. It says nothing about how the approach would perform on SGW's real historical data, which is itself flagged in the PRD as the single biggest open risk to validate before a real build.

## Future enhancements

Per the PRD's Phase 3+: additional hazards (flooding, heatwave, wildfire) and asset domains (water treatment, pumping stations), network-topology-aware consequence modelling, and confidence-tiered autonomy once the model has an operational track record.
